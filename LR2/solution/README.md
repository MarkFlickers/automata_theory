# Лабораторная работа № 2

Каркас программы структурного синтеза автомата Мили (вариант 1, прямое кодирование состояний). Реализованы чтение входных файлов, запуск программы из ЛР1 для минимизации каждой СДНФ, запись `output.txt` и `check.txt`, сравнение с проверочным словом. Этапы 1–2 и проверка по МДНФ оставлены в местах, помеченных `TODO`, в `src/StructSynthesis.cpp`.

## Как пользоваться каркасом

Начни с `src/main.cpp`: там видна последовательность работы. Затем открой рядом
`include/StructSynthesis.hpp` и `src/StructSynthesis.cpp`. Выполняй `TODO [1]`,
`TODO [2]`, `TODO [3]` по порядку. Поля для первого этапа уже предложены в заголовке;
при необходимости добавляй свои вспомогательные методы.

Каждая заготовка заканчивается `throw` с номером TODO. Удали его, когда реализуешь
этот метод. Сейчас остановка на `TODO [1]` — ожидаемое поведение каркаса.
Остальные проверки ошибок удалять не нужно.

| Файл | Назначение | Твоя работа |

## Общие соглашения

Это выбранные соглашения каркаса, а не дополнительные требования методички.
Если в материалах лекции используется другое представление входов, согласованно
измени кодирование, построение шкал и проверку. Номера в исходных файлах сохраняются.

### Номера, индексы и коды

- Номера входов, состояний и выходов в файлах начинаются с **1**.
- Индексы `Table::Value(input, state)` начинаются с **0**.
  `transitions_.Value(0, 0)` — переход из s1 при x1; его значение равно 2.
- `kUndefinedValue == 0` означает `-` в таблицах и проверочном слове.
  Это не номер состояния и не логический ноль в шкале.
- Прямой код состояния s — двоичная запись **s − 1** фиксированной длины:
  s1 → `000`, s2 → `001`, …, s8 → `111`.
- Код входа x — двоичная запись **x − 1**: x1 → `000`, …, x7 → `110`.
  Код `111` не используется.
- Для 8 состояний нужны 3 D-триггера, для 7 входных символов — 3 бита кода входа.
- `Table` владеет ячейками через `unique_ptr`: передавай таблицы по ссылке
  или перемещай. Для обхода достаточно `Value()`, `InputCount()`, `StateCount()`.

### Порядок битов и функций

Набор переменных: **a2 a1 a0 q2 q1 q0** — сначала код входа, затем код
текущего состояния; старшие биты слева. Позиция в шкале — число с этой двоичной
записью. Например, x2,s3 → `001010` → позиция 10 (индексация с нуля).

В `functions_` сначала идут **Q0, Q1, Q2**, затем **y1…y5**.
Q0 вычисляет младший бит следующего состояния, Q2 — старший.
Обозначения Q сохранены в стиле примера методички; значения этих функций
подаются на D-входы триггеров. Не путай Q с q — битами текущего состояния.

Выходы представлены отдельными функциями: yj означает «активен выход j».
Здесь не используется двоичное кодирование выходов. Для общего числа r триггеров
индекс Qj в `functions_` равен j, индекс yj — `r + j - 1`.

### Шкала, импликанты и символ «-»

`scale` — строка из `0`, `1`, `-`, по символу на каждый набор переменных.
Она задаёт функцию для ЛР1; текстовое выражение СДНФ отдельно строить не нужно.
Для 6 переменных длина равна 64. `mdnf` — список импликант после минимизации.
Например, `0--1--` истинна, если первый бит равен 0, а четвёртый равен 1.
Условия внутри импликанты соединяются И, импликанты между собой — ИЛИ.
Пустой список означает 0; импликанта из шести `-` означает 1.

| Где стоит `-` | Что он означает |
| --- | --- |
| В таблице f | Следующее состояние не задано: Q-биты свободны |
| В таблице g | Выход не задан: значения всех y-функций свободны |
| В шкале | Значение функции можно выбрать при минимизации |
| В импликанте | Эта переменная не влияет на данную импликанту |
| В ожидаемом S/Y | Любой полученный результат принимается |

Неопределённость f не означает неопределённость g, и наоборот.
Неиспользуемым кодам входов также соответствуют `-` в шкалах.

## Порядок реализации и самопроверка

### TODO [1]: EncodeStates

Заполни поля, предложенные в заголовке. Размеры таблицы дают количества входов
и состояний. В этом варианте номера выходов идут подряд от 1 до 5;
при подсчёте не учитывай `kUndefinedValue`. Вычисли разрядности, заполни
`stateCodes_` и проверь допустимость определённых номеров переходов.

Ориентир: **7 входов, 8 состояний, 5 выходов, 3 бита входа, 3 D-триггера**;
коды состояний — от `000` до `111`. Числа служат проверкой, вычислять их нужно
из таблиц. Готовый `PrintEncoding()` покажет заполненные поля.
После реализации программа дойдёт до `TODO [2]`.

### TODO [2]: BuildSdnf

Очисти `functions_`, подготовь шкалы и обойди пары «вход, текущее состояние».
Для Q используй код следующего состояния из f, для y — номер выхода из g.
Подробные шаги оставлены возле TODO в коде.

Ориентир: **8 функций по 64 символа**. Для x1,s1 таблицы задают s2 и y1,
поэтому в позиции 0 шкал Q0=1, Q1=0, Q2=0; y1=1, остальные y=0.
Позиции 56…63 соответствуют неиспользуемому коду входа `111` и остаются `-`.

После реализации программа выведет имена и длины шкал, вызовет ЛР1, создаст
`output.txt` и дойдёт до `TODO [3]`. Шкалы и МДНФ отдельных функций доступны
в `build/lab1_io/`. Наличие `output.txt` ещё не означает, что проверка пройдена.

### TODO [3]: Check

Возьми `expected.inputs` и только `expected.states.front()`.
На каждом шаге вычисляй все Q и y по МДНФ на **текущем** состоянии и только
после этого переходи в следующее. Не копируй ожидаемые S/Y в результат
и не моделируй по исходной таблице: это не проверит синтез.

Удобно самостоятельно выделить вспомогательный метод вычисления одной МДНФ
на наборе битов. Проверяй, что длина импликант совпадает с длиной набора.

Если истинна ровно одна yj, номер полученного выхода равен j. Если ни одна
или несколько — запиши `kUndefinedValue`: единственный номер восстановить нельзя.
При ожидаемом конкретном выходе сравнение выявит ошибку; при ожидаемом `-`
такой результат допустим. Независимая минимизация y-функций может дать эту
неоднозначность на наборах с неопределённым g. Ожидаемые выходы не должны
влиять на вычисление результата.

Верни 7 входов, 8 состояний (включая начальное) и 7 выходов.
Ожидаются состояния `1 2 8 1 4 3 8 3`, выходы `1 4 4 4 4 3 -`.
Последний выход не ограничен: конкретное значение после минимизации также
допустимо. Успешное завершение — `Check passed`.

Одно проверочное слово не проверяет весь автомат. Дополнительно сверяй значения
МДНФ на определённых клетках, особенно там, где f или g содержит `-`,
а другая таблица задаёт конкретное значение.

## Сборка

Из корневой папки **TA** сначала выполни `Set-Location LR2/solution`.
Если терминал уже в `LR2/solution`, переход не нужен. Команды ниже выполняются
из `LR2/solution`; нужны CMake, Ninja и компилятор C++20.

```powershell
cmake -S . -B build -G Ninja
cmake --build build
```

Вместе с `build/lab2.exe` собирается ЛР1 из `../../LR1/solution` — в `build/lab1/lab1.exe`. Другой путь к ЛР1 можно задать при конфигурации: `-DLAB1_SOURCE_DIRECTORY=путь`. Промежуточные артефакты — в `build/object`.

## Запуск

```powershell
Push-Location build
try { .\lab2.exe } finally { Pop-Location }
```

Терминал вернётся в `LR2/solution`. После изменения кода повторяй сборку и запуск.
После изменения входных файлов повтори также конфигурацию CMake, чтобы обновить
их копии в `build`. Редактируй исходные файлы в `solution`, а не копии в `build`.

В корневых настройках VS Code пока выбран проект ЛР1. Для сборки ЛР2 кнопками
редактора открой `LR2/solution` отдельной папкой и выбери компилятор в CMake Tools.
Приведённые команды работают независимо от этой настройки. Методичка указывает
Microsoft Visual Studio; текущая проверка каркаса выполнена с Ninja и GCC.
Если сдаёшь через Visual Studio, отдельно проверь сборку там.

Программа ищет файлы в текущей рабочей папке, поэтому запускается из `build`.
Старые выходные файлы могут остаться после неудачного запуска: ориентируйся
на сообщения текущего запуска.

| Файл | Назначение |
| --- | --- |
| `f_table.txt` | вход: таблица переходов (строки — входы, столбцы — состояния) |
| `g_table.txt` | вход: таблица выходов |
| `check_word.txt` | вход: проверочное слово, строки `X ...`, `S ...`, `Y ...` |
| `lab1_io/<имя>_scale.txt` | СДНФ функции, переданная в ЛР1 |
| `lab1_io/<имя>_mdnf.txt` | МДНФ функции, полученная от ЛР1 |
| `output.txt` | результат: МДНФ функций возбуждения D-триггеров и выходов |
| `check.txt` | результат: входы, состояния и выходы, полученные по МДНФ |

Путь к `lab1.exe` можно передать явно:

```powershell
.\lab2.exe "путь к lab1.exe"
```

Последняя команда выполняется из `build`.

## Если что-то пошло не так

- **Сообщение TODO:** реализуй указанный метод и убери завершающий `throw`.
- **Cannot open input file:** проверь рабочую папку и повтори конфигурацию CMake.
- **LR1 executable not found:** собери весь проект, проверь путь к ЛР1.
- **Состояния сдвинуты на единицу:** различай номер s, индекс s−1 и код s−1.
- **Выходы сдвинуты на шаг:** вычисляй их до изменения состояния.
- **МДНФ выглядит иначе:** минимальная форма может быть не единственной;
  сравнивай значения функций на заданных наборах, а не только текст импликант.
